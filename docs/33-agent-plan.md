## 1. Бизнес-гейты и что они требуют

### Гейт A — «можно показывать цеху» (1–2 недели)

Цель: 3 мастерские смотрят демо, 1–2 берут платный пилот. Продукт не должен
тормозить, путать и падать. AI-чат на этом гейте **не нужен**.

### Гейт B — «первые платные пилоты» (2–4 недели)

Цель: 3 пилота, €450–750, 2 отзыва. Нужен сквозной путь «данные клиента →
проект → 3D/PDF → смета/раскрой → выгрузки → передача цеху».

### Гейт C — «AI-копайлот» (3–4 недели)

Цель: сократить ручную сборку, получить «вау» на демо, удержать 5–10
клиентов. Нужен контракт операций, preview/diff, сессия, чат.

### Гейт D — «масштаб» (2–3 месяца)

Цель: 10–20 подписок / white-label. Нужны мультиарендность, роли, биллинг,
шаблоны, локализация. Не начинать раньше 10 платящих.

### Гейт E — «форк по стройке/дому» (3–6 месяцев)

Цель: пилот с застройщиком/архитектором. Нужно выделить общее ядро и
схему дома. Не начинать раньше, чем мебельный продукт даёт кэшфлоу или
есть оплаченный пилот.

## 2. Бэклог: Гейт A — демо для цеха

### A0. Прод жив: деплой с откатом и сторож ✅ (2026-10-29)

**Зачем:** 29.10 сайт висел 26 часов после добавления `reportlab` —
демо для цеха могло открыться вечным спиннером.

**Сделано:** `tools/deploy.sh` (тесты → метка `:previous` → сборка →
healthy → smoke → откат), `tools/health_watch.sh` + systemd-таймер каждые
5 минут (один перезапуск, потом алерт), uvicorn без `--reload` в проде,
`compose.dev.yaml` для разработки. Проверено: остановленный API поднят за
~20 с, искусственный сбой health привёл к откату. Детали —
`docs/34-deploy-and-monitoring.md`.

**Осталось:** алерт в Telegram (нужен токен бота), ежедневный `pg_dump` с
ротацией, сборка образов в CI вместо ручной.

### A1. Замер 3D на целевом железе

**Зачем:** без чисел «тормозит» — это ощущение. Нужен baseline, иначе
оптимизация наугад.

**Где:** `apps/web/src/render3d/babylonScene.ts`, `View3D.vue`,
`tests/e2e/perf.mjs`, `docs/31-device-checklist.md`.

**Шаги:**
1. Включить `?perf=1`, снять FPS/время кадра на 5/15/30 модулях.
2. Записать: FPS, draw calls, meshes, materials, textures, время загрузки.
3. Проверить на ноутбуке и телефоне (или в реальном браузере, не software GL).
4. Записать в `docs/35-3d-perf-baseline.md`.

**Приёмка:** таблица «сцена → FPS → draw calls → загрузка»; понятно, что
именно тормозит.

**Оценка:** 0.5–1 день.

### A2. Оптимизация 3D по результатам A1

**Зачем:** если демо лагает, цех не поверит продукту.

**Где:** `render3d/babylonScene.ts`, `View3D.vue`.

**Шаги (по необходимости, не всё сразу):**
- thin instances / merging по материалу;
- LOD для фурнитуры и мелких деталей;
- culling по комнате/камере;
- pixel ratio cap, render scale;
- отключение теней/SSAO на слабых;
- заморозка материалов, отказ от пересборки всей сцены на каждое изменение;
- прогрев сцены и кэш геометрии.

**Приёмка:** 5 модулей ≥ 45 FPS, 15 ≥ 30 FPS, 30 ≥ 24 FPS на ноутбуке;
телефон ≥ 24 FPS на 15 модулях; визуально без регрессий; `tests/e2e/perf.mjs`
зелёный.

**Оценка:** 2–4 дня.

### A3. Режимы «Мастер» и «Эксперт»

**Зачем:** после QuickStart пользователь попадает в «кабину самолёта».
Новичку нужен линейный путь, эксперту — все панели.

**Где:** `App.vue`, `QuickStart.vue`, `TopBarMenu.vue`,
`state/project.ts`, `styles/`.

**Шаги:**
1. Добавить `ui.mode: 'master' | 'expert'`, по умолчанию `master` для новых.
2. В мастере скрыть продвинутые панели, оставить: комната → проёмы →
   сценарий → результат.
3. Одна главная кнопка на экран.
4. Переключатель в меню, запоминать выбор.
5. Не ломать экспертный режим.

**Приёмка:** новый пользователь собирает кухню за ≤ 10 минут; 5 тестов,
4 без подсказок; эксперт видит всё как раньше.

**Оценка:** 2–3 дня.

### A4. «Следующий шаг» в статусбаре

**Зачем:** пользователь не должен думать, что делать дальше.

**Где:** `StatusBar.vue`, `state/project.ts`.

**Правила:**
- нет комнаты → «Задайте комнату»;
- нет модулей → «Добавьте модуль»;
- есть ошибки → «Исправьте расстановку (N)»;
- всё ок → «Скачайте проект».

**Приёмка:** в каждом состоянии ровно один CTA; клик ведёт к действию;
нет ложных «ок».

**Оценка:** 0.5–1 день.

### A5. Ошибки с действием

**Зачем:** сейчас коды переведены, но не все ведут к объекту. Цех/новичок
не понимает, что делать.

**Где:** `LayoutPanel.vue`, `state/project.ts`, `furniture_core/scene.py`,
`layout.py`.

**Шаги:**
1. Единый `issue`: `code`, `severity`, `object_id`, `message`, `fix`,
   `auto_fixable`.
2. Кнопка «Показать» — фокус в 3D/плане.
3. Кнопка «Исправить» — только безопасное: нормализация, прижатие к стене,
   разведение декора.
4. Словарь кодов в `docs/29-furniture-standards.md`.

**Приёмка:** 90% ошибок имеют объект и действие; 0 сырых кодов; тесты
`scene.py`/`layout.py` зелёные.

**Оценка:** 1–2 дня.

### A6. Один сквозной демо-проект

**Зачем:** продавать нужно не фичи, а готовый результат.

**Где:** `projects/demo-*`, `ProjectResult.vue`, `exports`.

**Шаги:**
1. Кухня 3×4 и гардероб 2.5 м — два демо.
2. Пройти путь: комната → проёмы → сценарий → 3D → смета → раскрой →
   выгрузки.
3. Записать сценарий демо на 5 минут.
4. Проверить на телефоне.

**Приёмка:** демо проходит без ошибок; экспорт XLSX/DXF/SVG/PDF не пустой;
сценарий укладывается в 5 минут.

**Оценка:** 1–2 дня.

## 3. Бэклог: Гейт B — первые платные пилоты

### B1. Сквозной «проектный пакет»

**Зачем:** это то, за что платят €150–250.

**Шаги:**
1. Один экран/поток: данные клиента → проект → 3D/PDF → смета → раскрой →
   присадка → фурнитура → выгрузки.
2. Никакого ручного JSON.
3. Чек-лист «готово к производству»: 0 ошибок, все выгрузки, версия.

**Приёмка:** один проект собирается за 30–60 минут без ручных правок JSON.

### B2. Клиентская ссылка

**Зачем:** клиент должен согласовать, а не пересылать PDF.

**Шаги:**
1. Read-only ссылка на проект: 3D/план, смета, статус.
2. Без логина, по токену; на телефоне.
3. Комментарий/«Согласовано»; версия фиксируется.

**Приёмка:** клиент открывает на телефоне, видит 3D и смету, может
согласовать; доступ нельзя угадать.

### B3. Версия перед отправкой

**Зачем:** если клиент согласовал, проект нельзя молча менять.

**Шаги:** снимок версии при отправке; восстановление; бейдж «отправлено».

**Приёмка:** после правок можно вернуться к согласованной версии.

### B4. Пакет выгрузок

**Зачем:** цех должен собрать без звонков.

**Шаги:** один клик — XLSX (детали, раскрой, присадка, фурнитура, смета),
DXF, SVG, PDF КП.

**Приёмка:** цех по выгрузке собирает без вопросов (пилот).

## 4. Бэклог: Гейт C — AI-копайлот

### C1. 12 типизированных операций

**Зачем:** ИИ не должен писать сырой JSON.

**Шаги:** Pydantic discriminated union + JSON Schema; 12 операций:
add/update/delete/move module, add/update/delete opening, add/update/delete
wall item, add/update/delete decor, set room/globals/materials/template.

**Приёмка:** `/api/ai/tools` отдаёт схемы; LLM вызывает без чтения исходников.

### C2. Preview/diff

**Зачем:** человек должен видеть, что изменится, до сохранения.

**Шаги:** `POST /preview` → before/after, changed objects, errors, cost,
warnings; без записи.

**Приёмка:** чат показывает «+3 модуля, смета +€420, ошибок 0» до apply.

### C3. Машинно-читаемая валидация

**Зачем:** ИИ должен сам исправлять, а не гадать.

**Шаги:** `code`, `severity`, `object_id`, `message`, `fix`, `auto_fixable`;
словарь кодов.

**Приёмка:** 90% ошибок имеют fix; ИИ выбирает fix без угадывания.

### C4. Дизайн-сессия

**Зачем:** чат — это UI, мозг — сессия.

**Шаги:** `POST /design/session`, `/plan`, `/apply`, `/undo`; шаги, версии,
решения человека.

**Приёмка:** сессия переживает перезагрузку; undo возвращает состояние.

### C5. Eval 20 сценариев

**Зачем:** «ИИ тупит» нужно измерять.

**Шаги:** 20 NL-сценариев, ожидаемые ограничения, метрики: успех, невалидные
операции, правки, время.

**Приёмка:** ≥ 80% успеха, 0 испорченных проектов, ≤ 2 правки в среднем.

### C6. Чат в интерфейсе

**Зачем:** пользователь просит — ИИ делает, человек подтверждает.

**Шаги:** панель, история, карточки действий, preview, apply/undo,
подсветка в 3D/плане, ограничения (не сохранять при ошибках, не удалять без
подтверждения, не выдумывать размеры).

**Приёмка:** 10 сценариев в чате, 0 испорченных проектов, undo работает.

## 5. Бэклог: Гейт D — масштаб (не сейчас)

- Мультиарендность и роли (владелец/админ/мастер/наблюдатель).
- Биллинг (Stripe/Revolut), тарифы, лимиты.
- Шаблоны проектов, библиотека модулей, локализация RO/RU/EN.
- White-label: бренд, домен, цвета, выгрузки.
- Онбординг self-serve, аналитика, поддержка.

**Условие старта:** 10 платящих клиентов или 3 white-label пилота. До этого
не строить.

## 6. Бэклог: Гейт E — форк по стройке/дому (потом)

- Выделить общее ядро: единицы, материалы, цены, экспорт, валидация.
- Схема дома: слои, этапы, объёмы, смета (`docs/27-house-fork.md`).
- MVP: комната → слои → объёмы → смета → PDF.
- Пилот с одним застройщиком/архитектором.

**Условие старта:** мебельный продукт даёт кэшфлоу или есть оплаченный
пилот по дому. Не начинать раньше.

## 7. Протокол работы агента

1. Прочитать `AGENTS.md`, `docs/32`, `docs/33`.
2. Одна сессия — одна задача из бэклога. Не тащить рефакторинг параллельно.
3. Перед началом: `python3 tests/golden.py` и профильный тест.
4. После: профильные тесты + `tsc --noEmit` + `npm run build`.
5. Обновить `docs/14-worklog.md` и статус в `docs/26`/`docs/33`.
6. Коммит — только по просьбе; один коммит = одна задача.
7. Если ИИ начал тупить — сузить до одного файла и одного теста, не
   уговаривать.
8. Не выдумывать размеры, не менять `specs/` цены, не трогать golden без
   причины.
9. Если задача требует бизнес-решения — остановиться и спросить.

**Формат отчёта:**
- что сделано;
- файлы;
- тесты/замеры;
- риски;
- следующий шаг.

## 8. Что не делать

- Не строить чат раньше контракта операций.
