# 12 — Веб-конструктор мебели и интерьера (архитектура)

> Статус: **рабочий прототип**. Дата обновления: 2026-10-25.
> Текущее состояние и что дальше — `docs/13-editor-state.md`.
> Цель: веб-редактор «комната → мебель → деталировка → 3D/видео»,
> где правила проекта (`docs/`, `specs/`) — исполняемый код, а не советы.
>
> **Рендер в браузере — Babylon.js (WebGL)** для основного 3D-вьюпорта.
> **Canvas 2D** остаётся для плана, миниатюр и схематичного превью деталей.
> Финальный фотореализм и видео — Blender на сервере/локально.

## 1. Резюме решения

Строим **не «ещё один 3D-редактор», а параметрический конструктор с деталировкой**.
Ключевое отличие от Planner5D/SketchUp: на выходе не картинка, а **валидированная
деталировка, раскрой, присадка и схема сборки**.

Два главных принципа:

> **1. Один движок расчёта — несколько рендереров.**
> Python-движок (`tools/`) — единственный источник истины.
> 2.5D в браузере, SVG для печати и Blender для видео показывают **один и тот же
> `SceneSpec`**.

> **2. Два рендерера на одну модель.**
> Babylon.js даёт тени, материалы и выбор деталей; Canvas 2D даёт быстрый план,
> миниатюры и точные схемы. Оба читают один `SceneSpec` из движка.

Поэтому в вебе **не переписываем правила мебели на TypeScript**. В браузере —
только раскладка (позиции, повороты, привязки), а деталировка/кромка/присадка/
раскрой считаются тем же кодом, что уже работает.

## 2. Что уже есть и что переиспользуем

| Актив | Роль в новой системе | Что доработать |

```
      │  позиции,       │  (drag, snap,         │  детали, кромка,  │  (по commit)
      │  привязки       │   коллизии)           │  присадка, раскрой│
      └───────┬────────┘                        │  валидатор        │
              │                                 └─────────┬─────────┘
              │                                           │
              └──────────────► SceneSpec v2 ◄─────────────┘
                        (комната + мебель + материалы)
                                    │
              ┌─────────────────────┼─────────────────────┐
      ┌───────▼────────┐    ┌───────▼────────┐    ┌───────▼────────┐
      │ 2.5D Canvas    │    │ SVG-экспорт    │    │ Blender (сервер│
      │ интерактив     │    │ печать/PDF     │    │ / локально)    │
      │ 60 fps, без GPU│    │               │    │ 3D, видео      │
      └────────────────┘    └────────────────┘    └────────────────┘
```

Раскладка отдельно от деталировки:

- при перетаскивании шкафа **не меняются** его детали — меняется только transform;
- пересчёт деталировки нужен при смене параметров (ширина, двери, материал) —
  это десятки миллисекунд на сервере, дебаунс 150–300 мс;
- значит, дублирования правил нет: TS знает только про коробки и позиции.

**Инвариант из `AGENTS.md`**: каждая секция — независимый модуль (свои стенки,
своя крышка), общих стенок нет, каждому полотну — своя стойка. Это проверяет
движок, а UI обязан не предлагать невозможных конфигураций.

## 4. Canvas 2D: план, миниатюры и превью

Это не «урезанный 3D»: ортографическая проекция даёт точные размеры и позволяет
менять ракурс, оставаясь векторно-честной.

### 4.1. Что делает

- **Ортографическая камера**: yaw (поворот вокруг Z), pitch (наклон), zoom.
  Перспектива не нужна и только мешает замерам.
- **Проекция 8 углов коробки → 6 граней → отсечение задних → сортировка по
  глубине → заливка + обводка.**
- **Плоское затенение** по нормали: `I = ambient + diffuse · max(0, n·L)`.
  Одна ключевая световая + подсветка сверху. Этого достаточно, чтобы панели
  читались как объём.
- **Режимы отображения**: «реалистичный» (цвет + текстура), «чертёжный»
  (белые грани, чёрные рёбра, скрытые линии убраны), «рентген» (все рёбра).
- **Виды**: план, фасад, бок, изометрия 3/4, свободный орбит (drag), «вид на
  выбранное». Переключение — плавный интерполяцией yaw/pitch за 200 мс.

### 4.2. Почему Canvas 2D, а не SVG в интерактиве

- SVG удобен для экспорта, но 600–1500 узлов на кадр при перетаскивании — lag.
- Canvas 2D держит 60 fps на 1000+ полигонов и не требует зависимостей.
- Хит-тест делаем сами: храним проецированные полигоны в порядке отрисовки,
  клик → point-in-polygon по списку сверху вниз.
- **Экспорт — отдельный бэкенд того же сцены**: те же полигоны пишем в SVG
  (для PDF, карточек, схем сборки). Геометрия считается один раз.

> Итог: один `buildScene(SceneSpec, camera) → Polygon[]`, два потребителя:
> Canvas (интерактив) и SVG (печать). Тесты — на `Polygon[]`, не на пикселях.

### 4.3. Текстуры без WebGL

Ортографическая проекция — аффинная, поэтому прямоугольная панель проецируется
в **параллелограмм**. Значит, текстуру можно натянуть точным аффинным
преобразованием через `CanvasPattern` + `setTransform` по трём углам грани.

- Бесшовный декор генерируется один раз в offscreen-canvas (процедурный шум
  под дерево) или грузится картинкой.
- Направление волокна берётся из данных движка (`grain`) — визуал совпадает
  с раскроем.
- В SVG то же самое делается через `<pattern patternTransform>`.

Это закрывает требование «менять паттерны и цвета» без 3D и без шейдеров.

### 4.4. Интерфейс рендерера (задел на WebGL)

```ts
interface SceneRenderer {
  render(scene: SceneSpec, camera: Camera, sink: CanvasSink | SvgSink): void;
}
```

Сегодня — `Canvas25DRenderer`. Завтра, если понадобится, — `ThreeRenderer`
с тем же входом. Приложение и модель данных не меняются.

### 4.5. Производительность

- Перерисовка только по «грязному» флагу (`requestAnimationFrame`), не в цикле.
- Canvas подписан на счётчик версии документа, а не на глубокую реактивность Vue:
  реактивность — для панелей, рендер — по dirty-флагу.
- Полигоны и порядок сортировки кэшируются на камеру; при движении мебели
  пересчитывается только изменённая часть.
- Потолок сцены: ~2000 граней — с запасом для квартиры.
- Никаких теней и постобработки: глубина читается за счёт затенения и обводок.

## 6. Координаты и камера

Модель (мм): `X` — длина, `Y` — глубина (**0 = фасад**, растёт вглубь), `Z` — вверх.

Экран считается один раз, в одном месте:

```ts
// Ортографическая проекция. Никаких других пересчётов в коде.
function project(p: Vec3, cam: Camera) {
  const cy = Math.cos(cam.yaw), sy = Math.sin(cam.yaw);
  const cp = Math.cos(cam.pitch), sp = Math.sin(cam.pitch);
  const right = [cy, -sy, 0];                  // экранное X
  const up    = [-sy * sp, -cy * sp, cp];      // экранное Y
  const fwd   = [sy * cp, cy * cp, sp];        // в глубину (для сортировки)
  return {
    x: dot(p, right) * cam.zoom + cam.cx,
    y: -dot(p, up) * cam.zoom + cam.cy,
    d: dot(p, fwd),
  };
}
```

Пресеты камеры: план (`pitch=90°`), фасад (`yaw=0°, pitch=0°`), бок
(`yaw=90°`), изометрия (`yaw=-35°, pitch=25°`). Проверка — тест проекции
эталонного шкафа на всех видах.

Blender: `(x, y, z) / 1000` — как сейчас в `blender_build.py`.

## 7. Стек

| Слой | Выбор | Почему |
|---|---|---|
| Сборка | **Vite + TypeScript** | dev-сервер, HMR, ноль рантайма |
| UI | **Vue 3** (`<script setup>`, TypeScript) | родной стек; без three.js/R3F аргумент за React исчез |
| Стили | **чистый CSS**: `@layer`, CSS-переменные, BEM-именование | без Tailwind, препроцессоров и UI-китов |
| 3D | **Babylon.js** (`render3d/`) | тени, материалы, выбор деталей, режимы качества |
| 2.5D | **Canvas 2D API** + свой `vec/mat` | план, миниатюры, схематичное превью |
| Состояние | **встроенная реактивность Vue** (`reactive`/`shallowRef`/`computed`) + снапшоты для undo | без Pinia/Vuex/Zustand/Immer |
| Валидация | **Pydantic на сервере** + ручные проверки в TS | без Zod; JSON Schema — документация |
| Backend | **Python 3.12 + FastAPI** | движок уже Python; Blender тоже Python |
| Хранение | **файлы на диске**: `projects/<id>/project.json` | локальный режим, без БД |
| Экспорт | `ezdxf`, `openpyxl`, свой SVG-писатель, WeasyPrint | уже используются |
| Blender | **локальный CLI** `blender -b -P …` | без очередей и облака |

Правило: **никаких UI-библиотек**. Кнопки, панели, селекты, меню, модалки,
тултипы — на нативных элементах и своём CSS:

- `<dialog>` для модалок;
- Popover API для меню и тултипов;
- `<select>`, `<input type="number">`, `<details>` — нативные;
- иконки — один inline SVG-спрайт;
- шрифты — системный стек (без веб-шрифтов);
- тёмная/светлая тема — `prefers-color-scheme` + `[data-theme]`.

Бандл: Vue + Babylon.js; режим «Каркас» снижает нагрузку на слабых GPU.

### Чего НЕ делать

- Не тащить второй 3D-движок: в браузере уже Babylon.js.
- Не тащить OpenCascade/Replicad: корпусная мебель — коробки и панели.
- Не строить свободное 3D-моделирование: пользователь **ставит модули и меняет
  параметры**.
- Не считать деталировку на клиенте: BOM всегда с сервера.
- Не ставить Tailwind, shadcn, Radix, MUI, Ant, Bootstrap, CSS-модули-как-фреймворк.

## 8. UX редактора

**Один документ — три вида.**

1. **План (ортокамера сверху).** Рисование/редактирование стен, размерные цепочки,
   перетаскивание модулей вдоль стен, магнитные привязки (углы 90°, стыки,
   выравнивание фасадов). Основной режим раскладки.
2. **2.5D.** Изометрия/фасад/орбит для проверки вида и материалов. Здесь же
   открывание дверей и выкат ящиков (те же данные `hinge`/`drawer_id`).
3. **Модуль (inspector).** Ширина/высота/глубина, двери, полки, ящики, каркас
   (`inset`/`overlay`), фурнитура, фасад/корпус, кромка.

Планировка: **split view** «план + 2.5D» с синхронным выделением. Дёшево —
оба вида рисует один и тот же Canvas-рендерер с разными камерами.

Принципы, которые решают «удобно/неудобно»:

- **Линия (run), а не одиночные шкафы.** Тянешь линию вдоль стены; модули
  добавляются/удаляются, ширины перераспределяются, остаток закрывается
  планкой-заполнителем.
- **Размеры вводятся числами**, а не только мышью. Каждое поле — с минимумом,
  максимумом и объяснением (почему нельзя дверь 700 мм).
- **Валидатор виден.** Ошибки — на элементе и в панели; выгрузка блокируется,
  пока есть ошибки (правило проекта).
- **Undo/redo на всё** — снапшоты документа (50 шагов, `structuredClone`).
- **Автосохранение** — debounce + локальный файл через API.

MVP-скоуп комнаты: **прямоугольник + стены заданной длины**, проёмы (дверь/окно).
Полигональные комнаты и эркеры — фаза 2.

## 9. Материалы и декоры

- `Material`: `kind` (ЛДСП, МДФ, HPL, стекло, металл), `thickness`, `decor`
  (base color + карта текстуры + roughness), `edge` (толщины кромки).
- **Декор = текстура + тинт**, а не десяток отдельных материалов. Один
  бесшовный атлас на семейство, аффинное натяжение по грани (см. §4.3).
- Назначение поверхности: `facade / corpus / worktop / back`. Переопределение
  на уровне модуля и секции.
- Кромка — **отдельная геометрия** из данных движка (реальные 0,4/1/2 мм):
  визуал совпадает с производством.
- MVP: 8–12 цветов + 3 текстуры. Каталог Egger/Kronospan — данные.

## 10. Экспорт

| Что | Формат | Где считается |
|---|---|---|
| Деталировка | XLSX / CSV / JSON | Python |
| Раскрой | SVG (по листам) + КПД | Python (MaxRects) |
| Присадка | DXF по деталям + сводка | Python |
| Виды / схема сборки | SVG (из 2.5D-сцены) | TS (те же полигоны) |
| Смета/КП | PDF | Python (WeasyPrint + Jinja2) |
| Обмен | `SceneSpec v2` JSON | Python |
| 3D | PNG/MP4 | Blender |

**SVG-экспорт из 2.5D — ключевой бонус**: виды, изометрия, разнесёнка и схема
сборки получаются векторными, без 3D-рендера. Их можно вставлять в PDF и карточки.

Цены — отдельный слой `specs/prices-*.yaml` (материал за м², кромка за м.п.,
фурнитура за шт., работа). Не правила, а настройка.

## 11. Blender-пайплайн (локально)

```
кнопка «Рендер» → POST /api/projects/{id}/render
   → subprocess: blender -b -P tools/blender_build.py -- scene.json out/ <preset>
   → файлы в projects/<id>/renders/
   → прогресс в UI (SSE)
```

На локальном этапе — без Redis/S3/очередей: один процесс, один пользователь.
Интерфейс API сразу делаем таким, чтобы позже подменить исполнителя на очередь.

Пресеты: `stills` (Cycles), `turntable` (EEVEE), `walkthrough`, `explode`.

Практика:

- **EEVEE headless требует GPU/EGL**; на CPU безопасный дефолт — Cycles + OIDN.
- Стилл 1080p, 64–128 сэмплов, AgX, HDRI — 1–3 мин CPU.
- Видео 200–300 кадров — EEVEE на GPU; Cycles для видео слишком дорог.
- Один `SceneSpec` → одинаковая геометрия в 2.5D и Blender. Расхождение — баг.

## 18. Каталог объектов и модалка добавления (2026-10-23)

Единая точка добавления — модалка `AddObjectModal`, а не панель пресетов.
Причина: у объекта есть **тип** (мебель, проём, позже — техника, декор), а у типа
— свои настройки и своё поведение (проём закреплён за стеной, мебель стоит на
полу). Модалка сразу задаёт эту ось.

```
Тип объекта
├── Мебель        → MODULE_PRESETS (group: Тумбы/Ящики/Мойки/…)
│                    addInstance(key, x, y, override)
└── Окна и двери  → Opening (wall, x, w, z0, z1)
                     addOpening(kind, opts)
```

Что уже есть:

- вкладки «Мебель» / «Окна и двери»;
- поиск по названию/подсказке/группе и чипы-фильтры групп;
- карточки каталога с группой и подсказкой;
- правая колонка настроек: W/H/D, двери/ящики/полки, каркас, петли,
  направляющие; для проёма — стена, ширина, Z0/Z1;
- закрытие по клику вне окна и `Esc`; добавленный объект сразу выделяется.

Правило роста: **новый тип объекта = новая вкладка/секция каталога и своя
функция создания**, а не ветка в существующей. Общие поля (размеры, координаты,
материалы) переиспользуются; специфичные (направляющие, присадка, вырез) живут
в настройках типа.

Быстрая карточка (`ObjectModal`, режим quick) появляется рядом с курсором;
детальный режим (`ModuleWorkbench`) открывается справа и не перекрывает
выбранный объект. На телефоне — bottom sheet и полноэкранный режим.


## 19. Комната, стены и проёмы (2026-10-24)

`room.outline` — контур в плане (мм). Если не задан, используется прямоугольник
`w × d`. Стены строятся между соседними точками; нормаль автоматически
разворачивается внутрь контура (point-in-polygon).

- **Любое число стен и углы** — контур из N точек; 3D-рендер, план и fit
  используют один и тот же `roomWalls()`.
- **Перегородки** — `room.partitions: [{a, b}]`. Рисуются с двух сторон; проём
  на перегородке общий: одна дверь, одно состояние `open`.
- **Проёмы** — `room.openings[]`, `wall` = индекс стены/перегородки. Ширина,
  Z0/Z1, сторона петли (`hinge`), угол (`angle`).
- **Проверка планировки** — модуль не может выйти за контур: проверяются 4 угла
  повёрнутого габарита (`roomContains`).
- **Пол** — триангуляция ear clipping; UV-рамка общая на всю комнату, поэтому
  нет диагональных швов текстуры.

Ограничение: комнаты как отдельные сущности пока не выделены; роль «комнаты»
выполняют папки + перегородки. Стены общие на проект.

## 20. Конфигурация корпуса и API для ИИ (2026-10-24)

Поля изделия (`params`), которые понимает движок:

| Поле | Значения | Смысл |
|---|---|---|
| `t` | 10/16/18/22 | толщина ЛДСП |
| `back` | dvp/same/cardboard/none | задняя стенка |
| `backT` | 1…18 | толщина задней |
| `roof` | bool | крыша |
| `reinforce` | auto/on/off | царги 60 мм |
| `mount` | floor/wall | напольный/навесной |
| `plinthH` | 0…300 | цоколь (0 — нет) |
| `worktopT` | 0…80 | столешница (0 — нет) |
| `fronts` | `[{type,count,height}]` | фасады сверху вниз |
| `cutouts` | `[{x,y,w,h}]` | вырезы в столешнице |
| `handle` | id из `specs/hardware.yaml` | ручка фасадов и её цена |

Правило: **геометрию и размеры считает только движок**; UI передаёт параметры,
получает `bom`, `objects`, `drilling`, `validation`, `dims`, `cutouts`.

API для ИИ-агента:

```
GET  /api/catalog                 пресеты, толщины, правила
GET  /api/shop                    профиль цеха
POST /api/solve                   полный расчёт
POST /api/validate                проверка без полного результата
GET  /api/ai/guide                инструкция и список действий
GET  /api/projects/{id}/summary   сводка проекта + проверки модулей
POST /api/projects/{id}/actions   пакет правок; commit=false — предпросмотр
```

Действия: `add_instance`, `update_instance`, `delete_instance`, `add_opening`,
`set_room`. `commit=true` пишет проект; по умолчанию — только возвращает
изменённый документ. Необратимые операции — с подтверждением человека.

## 22. Обновление 2026-10-25: мобильный режим, переменные, материалы, КП

- **Мобильная раскладка** (`@media max-width: 900/640px`, `pointer: coarse`):
  панель «Объекты» выезжает снизу, нижняя навигация «3D / Объекты / ＋Объект»,
  объектный режим разворачивается на весь экран, быстрые действия — bottom sheet,
  крупные поля и кнопки, `100dvh` и safe-area.
- **Глобальные переменные проекта** (`project.globals`): толщина ЛДСП, задник,
  каркас, петли, направляющие, цоколь, столешница, зазоры. Новые модули
  наследуют значения; ручная правка поля помечает его как переопределение
  (`instance.overrides`), сброс — к глобальным.
- **Материалы на уровне модуля** (`instance.materials`): цвет, рисунок, текстура
  перекрывают материалы проекта; проект задаётся в «Проект → Материалы».
- **Текстуры в Babylon**: `StandardMaterial.diffuseTexture`, масштаб по
  `texScale` и размеру детали; в Canvas-превью — прежний процедурный рисунок.
- **КП/печать**: форма с модулями, деталями, сметой и итогом; печать браузера
  сохраняет PDF.
- **Движок**: постформинг столешницы без кромки 2 мм; одинаковые детали
  сводятся в позиции; каталог петель по брендам (`specs/hardware.yaml`);
  зазоры фасадов можно переопределять на изделие.
- **Чистка**: удалены неиспользуемые компоненты (`View25D`, попапы, старый
  инспектор) и архивный Canvas-рендерер.


## 23. Версии проекта (2026-10-25)

Снимок — полный `project.json`, сохранённый отдельно от текущего проекта.
Работает и в файловом режиме, и в PostgreSQL.

```
GET    /api/projects/{id}/versions            список (новые сверху)
POST   /api/projects/{id}/versions            снимок текущего проекта {name?}
GET    /api/projects/{id}/versions/{vid}      документ версии
POST   /api/projects/{id}/versions/{vid}/restore  откат {backup?: true}
DELETE /api/projects/{id}/versions/{vid}
```

- Файлы: `projects/<id>/versions/<vid>.json` (`{id,name,created,doc}`).
- БД: таблица `project_versions(project_id, id, name, doc, created)`.
- Перед откатом создаётся автоматический снимок текущего состояния.
- UI: `VersionsPanel` — снять снимок, список, восстановить, удалить; вход из
  TopBar «Версии» и из «Проект → Версии…». На мобильном доступно через
  «Проект».
- После восстановления проект нормализуется, пересчитывается и сохраняется.
